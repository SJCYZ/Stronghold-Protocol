# SDK 玩家生命值操作与救援插件设计

- 状态：待用户审阅
- 日期：2026-10-20
- 范围：为服务器端玩法插件增加结算后的玩家生命值操作，并实现“消耗生命值救援已淘汰玩家”的插件。

## 背景

当前 Match 的 `settle()` 先扣除本回合生命值，再立即对 LP 不高于 0 的玩家调用 `eliminate()`，随后设置 3 秒 SETTLE 截止时间并进入下一回合或结束对局。`PlayerState.eliminate()` 会释放棋子和装备库存、清空棋盘、手牌、临时区、商店、资金、待入账金币、赏金和待领取奖励。进入下一轮时，存活玩家把 `pendingFunds` 与新收入一并加入资金，再刷新商店。

现有 `sp:sdk@1` 没有 Match 生命周期、玩家 LP 读取或写入接口。界面插件桥是只读的，会拒绝 Match intent，因此不能单靠 UI iframe 实现救援按钮。当前 SDK 的战斗模拟插件与 Match 服务端权威状态相分离，生命值操作必须由服务端 Match 验证并执行。

相关实现：`server/match/match/settle.js`、`server/match/player/round.js`、`server/match/snapshot.js`、`shared/plugins/sdk.js`、`shared/plugins/ui.js`、`shared/protocol.js`。

## 目标

1. 服务器端玩法插件能在 LP 结算后读取对局玩家状态，并通过受限 SDK 接口修改生命值或复活待淘汰玩家。
2. 提供一个 `life-rescue` 脚本插件，生命代价可配置，默认 10。
3. 若本次结算产生待淘汰玩家，且有仍存活、支付后至少剩 1 LP 的真人救援者，开启 20 秒救援窗口。
4. 救援操作由原生游戏界面发起，并由 Match 服务端验证；不能依赖客户端状态或插件 iframe 的任意消息。
5. 救援者支付设定 LP 后，被救玩家以 1 LP 和淘汰前阵容、物品及结算后的可延续状态进入下一轮。
6. 每个被救玩家每局最多成功复活一次；救援者可在有其他合格目标时继续救援。
7. 无救援插件或没有可支付的真人救援者时，保持现有淘汰和 3 秒结算流程。

## 非目标

- 不开放客户端直接修改 LP，不暴露 `PlayerState` 可变对象。
- 不提供任意游戏阶段的资源修改接口；本次只增加结算期生命值操作。
- 不改变战斗模拟、战斗伤害结算和玩家原有 LP 损失规则。
- 不恢复淘汰玩家的旧商店；下一轮仍按正常规则重新生成商店。
- 不为救援窗口增加独立的进程恢复语义；沿用 Match 当前安全检查点回滚行为。
- 不扩展现有只读 UI 插件，使其能够提交 Match intent。

## 已确认规则

- 救援代价由插件设置，默认 10 LP，设置为正整数（拟限制在 1–100）。服务器使用锁定内容集中的设置值，不接受客户端自报代价。
- 20 秒从完成本次 LP 结算并公布待救目标时开始；结算窗口结束前不进入下一轮，也不提前结束比赛。
- 只有仍存活的真人玩家可以作为救援者；目标是本次结算进入待淘汰状态的玩家席位。
- 救援者支付后必须至少保留 1 LP。若 LP 不足以支付设定代价并保留 1 LP，按钮不可用，服务端也拒绝请求。
- 每个目标在整局中最多被成功救援一次。救援者没有额外的每局次数上限，但不得重复救同一目标。
- 多个救援者同时选择同一目标时，Match 依次处理请求，首个通过验证的请求成功，其余请求不扣 LP。
- 被救目标恢复为 1 LP，并恢复结算时淘汰清理前的棋盘、手牌、临时区、棋子和装备实例及其库存来源；库存占用必须精确恢复。
- 被救目标同时保留结算后资金、`pendingFunds`、剩余赏金、待领取奖励和个人选择。赏金场数沿用本次结算已扣减后的值；本次结算产生的待入账金币不重复计算。旧商店不恢复，下一轮重新刷新。
- 付款记入救援者的 `stats.lpLost`。复活不回退目标已结算的 LP 损失统计、伤害统计、赏金结算、盟约层数或其他本回合结算结果。
- 若没有合格真人救援者或没有待救目标，则不额外等待 20 秒，按现有结算时限完成清理/推进。

## 方案比较与选择

### 方案 A：受限的结算期 SDK 与专用救援动作（采用）

SDK 暴露服务器端结算回调、玩家 LP 只读视图和结算期生命值操作；插件登记救援行为与代价。原生游戏界面展示待救玩家及可支付状态，并发送专用救援 intent。服务端在 Match 状态机中保留待淘汰状态 20 秒，验证救援后恢复目标，超时后才完成原淘汰清理。

优点：满足插件实现与 SDK 可扩展的目标；服务端负责竞态、代价、复活次数及库存一致性；只扩展结算期，不开放其他阶段写权限。缺点：需要同时改 SDK、Match、协议和游戏内结算界面。

### 方案 B：通用插件动作框架

允许插件在多个 Match 阶段注册动作，再提供通用 LP 和玩家状态修改接口。未来其他插件可复用，但会扩大权限、协议和界面框架，超出本次一个结算期动作所需范围。

### 方案 C：救援完全内建

把救援判定和界面直接写入核心 Match，不提供 SDK 生命值接口。实现面较窄，但规则不能由用户要求的插件实现，后续插件也无法按相同生命周期操作 LP。

## SDK 与插件接口边界

新增 `match.life` 权限，只授予脚本/可信代码插件。建议 SDK 提供以下能力（最终方法名在实施计划中固定）：

- 服务器端 `postSettlement` 回调：在整批玩家 LP 与战斗结果结算后、下一轮推进前执行一次。浏览器模拟环境可以注册但不执行该回调，也不能调用写操作。
- 不可变玩家视图：至少提供玩家标识、真人/AI 标记、存活/待淘汰状态和当前 LP。
- 结算期 `changeLife`：以整数差值调整仍存活玩家 LP；执行时验证阶段、目标和结果范围，并由服务器更新 Match 状态与生命损失统计。
- 结算期 `revive`：只能作用于本次结算的待淘汰目标，将其恢复至指定正 LP，并恢复服务器保留的目标状态；同一目标成功后立即标记已救援。
- 救援动作处理器接收由服务端认证的救援者身份和目标 ID，不接收客户端指定的代价或救援者 ID。

接口不得返回玩家对象引用。SDK 不允许插件从浏览器端修改 LP，不允许插件在 COMBAT、PREP 或 RESULT 中调用上述写操作。缺少 `match.life` 权限时按既有插件权限错误机制拒绝注册或调用。

`life-rescue` 插件读取 `sp.settings.lifeCost`，在有待救目标和合格救援者时启用 20 秒救援动作。内容设置进入现有内容集身份哈希；改变设置会形成新的内容组合。插件脚本仍遵循既有服务器启用、锁定内容集和房间同意机制。

## Match、协议和界面行为

1. `settle()` 先完成现有 LP 扣除、战斗统计、奖励和赏金回合数结算。LP 不高于 0 的玩家进入“待淘汰”状态，不立即释放其阵容/装备库存。
2. 如果已启用救援插件且存在合格真人救援者，Match 保持 `PHASE.SETTLE` 并发布 20 秒 deadline、代价、待救目标和当前玩家是否具备支付能力。待淘汰玩家对外仍显示为已淘汰，不能执行普通 Match 操作。
3. 游戏原生 SETTLE 界面显示救援说明、待救目标、代价与倒计时；每个合格真人救援者可选择一个目标并提交专用 `g.rescue` intent。UI 插件桥和普通插件 iframe 保持只读。
4. Match 从已认证连接取得救援者 ID，并以服务端插件设置检查 cost。检查目标仍待淘汰、目标本局未被救、救援者存活且支付后至少有 1 LP、阶段未过期。验证和扣款/复活在一个 Match 处理步骤内原子完成。
5. 成功支付后立即重算救援者 LP、更新 `stats.lpLost`；目标设置为 alive、LP 1，恢复约定状态并标记本局已救援。广播新的玩家状态。重复或竞态失败不扣款。
6. 20 秒到期时，未救援目标执行原 `eliminate()` 清理。之后复用 `afterSettle()` 的存活检查：仍有人存活则开始下一轮，否则结束比赛。
7. 无插件或无救援资格时沿用现有 3 秒 deadline，避免影响普通房间。

## 状态、库存与恢复

- 待淘汰期间服务端保留目标淘汰前的阵容/物品快照或等效状态。库存来源和装备占用必须保留；目标不能在待淘汰状态下操作阵容，其他玩家也不能借此重复占用/释放其库存。
- 复活时恢复棋盘、手牌、临时区、棋子和装备实例及库存来源，并重新计算目标的战场部署映射/合法性；资金、待入账金币、赏金、奖励与个人选择按确认规则恢复。商店槽由 `startRound()` 正常重刷。
- 为保持“每个被救玩家每局一次”，将救援标记放入该玩家可持久化的 Match 状态，并在新局时重置。
- 当前 `snapshot.js` 不保存 `SETTLE`：进程在窗口内重启时回到最近的安全检查点并重打该回合。救援付款、复活状态和一次性标记一同回滚，不出现只扣款或只保留复活标记的半状态；不新增结算窗口的断点续时功能。
- Match Worker 与本地 Match 共用同一状态机与 intent 处理；Worker IPC 不应有独立救援规则。

## 验收条件

1. 未声明 `match.life` 的插件无法注册或调用生命值写 API；浏览器模拟和 UI 插件无法改变 LP。
2. 无插件、无死者或无合格真人救援者时保持原有 3 秒结算和淘汰行为。
3. 有待救目标及合格真人救援者时，SETTLE 窗口准确为 20 秒；到期前不会进入下一轮或完成比赛。
4. 成功救援只扣除配置代价一次，救援者剩余至少 1 LP；被救者恰为 1 LP 并恢复约定的阵容、装备、库存来源、经济和待领取状态。
5. 多目标可分别救援；同一目标一局只能成功一次；同目标并发请求只有一个成功；救援者 LP 不足、非真人/已淘汰救援者、错误阶段、过期和重复请求均不能扣款。
6. 未获救玩家在窗口结束时按原淘汰流程释放库存；之后存活检查、结束条件和下一轮状态正确。
7. 本地 Match 与 Match Worker 路径都执行相同授权、竞态、时限和状态逻辑；安全检查点回滚时救援结果整体回滚。
8. SDK 成员表、权限/插件校验、API 文档、协议文档及插件说明反映新接口和服务端权威边界。

## 主要风险

- 现有审计假设 SETTLE 中 LP 为 0 的玩家已完全淘汰。加入待淘汰窗口后，审计规则需区分“待淘汰”与“清理完成”，且不能让 pending 玩家参与普通存活/下一轮判定。
- 棋子和装备库存以实例来源精确计账。复活必须恢复原实例及 `poolCopies` / `itemPoolCopies`，不能按 ID 重新推测，否则会错误占用或释放共享库存。
- 在 `SETTLE` 中回调和 intent 需要通过本地与 Worker 同一 Match Host 路径执行；UI 更新只是呈现，不构成授权证据。
- `pendingFunds` 已包含本回合结算收入；复活时恢复其结算后值，不能重跑奖励派发，否则会重复入账。
- 复活后的旧棋盘需要在下一轮新部署图上重新验证，保留既有非法站位驱逐规则。
