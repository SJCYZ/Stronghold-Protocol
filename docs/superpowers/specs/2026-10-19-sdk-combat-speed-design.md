# SDK 战斗调速时钟设计

- 状态：待用户审阅
- 日期：2026-10-19
- 范围：向玩法插件 SDK 暴露服务端权威的战斗阶段时钟和调速接口，支持插件按战斗已过去时间分阶段加速。

## 背景

当前 SDK 明确不提供时钟；插件可以使用模拟器战斗钩子中的 `after` / `every`，但它们属于单个模拟实例。对局服务端在创建 Match 时设置固定 `gameSpeed`，并用它计算客户端战斗经过时间、战斗结果期限、服务端模拟节奏和 Boss 时钟。客户端收到 `b.start` 时也只拿到当前速度，战斗开始后没有服务端调速消息。

因此，仅在插件模拟代码中设置本地速度会让不同玩家、观战者和服务端接管模拟出现时钟分歧。调速必须由 Match 服务端统一控制，再同步给所有战斗视图。

## 目标

1. 插件能在服务端读取当前战斗阶段的逻辑经过时间，并注册按该时间触发的一次性或周期回调。
2. 插件能将当前对局战斗速度设为 `0.1` 至 `3.0` 之间、步进为 `0.1` 的值。
3. 速度变化对同一对局的参与者、观战者、服务端模拟和接管路径一致。
4. 暂停冻结逻辑时钟；恢复、重连和进程恢复均能沿用当前阶段时间及速度。
5. 未声明新权限的插件及无插件对局保持现有默认速度 `2.0` 和现有行为。

## 非目标

- 不改变战斗规则、模拟结果或内容插件可修改的游戏数值。
- 不开放浏览器本地调速，不接受客户端发起的速度变更。
- 不向插件提供墙钟、系统时间或通用定时器。
- 不开放准备阶段、大厅或整局生命周期的速度控制。
- 不引入多个插件相互覆盖调速的优先级机制。

## SDK 接口

新增受 `clock.speed` 权限保护的服务端战斗时钟注册接口。推荐接口形状如下；实施时将其加入 SDK 成员清单、API 文档和插件权限校验：

```js
sp.clock.onPhase(({ phase, elapsed, after, every, setSpeed }) => {
  after(120, () => setSpeed(2.5));
  after(240, () => setSpeed(3.0));
});
```

- `onPhase` 在插件 setup 时注册阶段处理器；插件 `setup` 在服务端和浏览器模拟环境都会运行，但该注册只由服务端 Match Host 激活，浏览器端不运行时钟回调，也不具备调速能力。
- 到达每个新阶段时，服务端调用已注册的阶段处理器一次。`phase` 是服务端当前阶段标识；`elapsed()` 返回该阶段逻辑经过秒数。
- `after(seconds, callback)` 在阶段逻辑时钟达到指定秒数时执行一次；`every(seconds, callback)` 从注册时刻起按指定逻辑间隔重复执行。间隔必须为有限正数，阶段结束时自动取消未完成任务。
- `setSpeed(value)` 设置该对局的全局战斗速度。有效值为 `0.1, 0.2, …, 3.0`；不做四舍五入。非法值拒绝该次调用并记插件错误，不改变当前速度。
- 时钟回调沿用插件现有的执行预算、异常隔离和错误记录规则。回调不能访问墙钟或自行创建定时器。
- 当前阶段时钟从 `0` 开始；速度在阶段开始时恢复 `2.0`。同一插件可以在每阶段重新安排调速表。

同一内容集最多允许一个有效的 `clock.speed` 速度控制插件。若多个插件同时声明该权限，内容集组合阶段拒绝冲突，避免速度计划依赖插件加载顺序。其他 SDK 能力保持原权限和注册行为。

## 时钟语义

- 服务端维护一个单调递增的阶段逻辑时钟。逻辑时间按墙钟区间累计当前速度；切换速度时先按旧速度结算至切换时刻，再应用新速度。
- `after` / `every` 使用阶段逻辑秒，而非墙钟秒。若一段调度延迟使逻辑时间越过多个到期点，服务端按到期时间顺序补发回调；同一到期点按注册顺序执行。
- 暂停期间阶段逻辑时钟停止，调速回调不触发；恢复后从暂停时的逻辑时间继续。
- 每个新的活动战斗阶段实例重置阶段逻辑时间并恢复 `2.0`。同一阶段中的字段重建、Boss 轮次内场景切换和客户端接管不重置阶段时钟。
- 速度只决定逻辑时间相对于真实时间的推进速率，不改变模拟器内部的战斗规则或已发生的战斗事件。

## 服务端与协议行为

Match Host 是唯一速度权威。发生速度变化时，服务端先结算阶段逻辑时钟，再更新当前速度，并向该对局相关战斗视图广播一个新的服务端消息 `b.speed`。消息至少携带阶段/战斗实例标识、当前阶段逻辑时间、速度和服务端时间基准；客户端仅按此消息重定基准，不得上报或反向覆盖速度。

服务端需要将当前速度和阶段时钟纳入统一的 Match clock source，并更新所有依赖固定 `gameSpeed` 的战斗路径：客户端字段经过时间与结果期限、服务端 FieldRunner/HeadlessPacer、Boss 进度预算与加时钟、暂停/恢复、字段自然结束释放。新加入、重连及观战者通过 `b.start` 获得当前阶段逻辑时间与速度，不依赖曾收到的历史 `b.speed` 消息。

字段开始时间和字段逻辑经过时间必须由可变速时钟计算，不能继续使用 `墙钟差 × 当前速度`，否则中途变速会错误重算已过去时间。所有截止时间应由剩余逻辑时间映射到当前速度，并在变速时取消、重算或通过统一逻辑时钟调度。

## 恢复与兼容

- 检查点记录当前阶段逻辑时间、当前速度及回调注册顺序、到期时间和已触发状态。恢复时按同一内容集重新初始化插件回调，将检查点状态绑定到新调度器并从冻结的阶段逻辑时间继续；不重复触发已完成的一次性回调。
- 旧检查点缺少这些字段时，按该阶段已运行但未使用动态调速的原有时钟规则恢复，当前速度取 `2.0`；不得将旧检查点的阶段时间误认为零。
- `b.start` 保持旧字段兼容，新增的动态时钟字段供新客户端做重基准。新客户端仍能处理没有 `b.speed` 历史的恢复场景。
- 纯原版对局不注册调速控制器，行为、默认速度和协议处理维持现状。

## 验收条件

1. 权限缺失或值不在 `0.1` 至 `3.0` 的 0.1 步进集合中时，插件不能改变速度。
2. 按阶段逻辑时间注册的定时回调在变速和暂停后仍于正确逻辑秒触发，且阶段结束后不会继续触发。
3. 速度变化后，客户端、观战者、服务端模拟、Boss 进度/加时、结果期限及接管路径使用相同的经过时间。
4. 重连和检查点恢复后，当前速度、逻辑时间及待处理回调状态连续；已完成回调不重放。
5. 无调速插件的原版战斗仍保持默认 `2.0`，不改变战斗结果。
6. API/权限清单、插件 API 文档和协议文档反映新增接口及服务端权威边界。

## 主要风险

当前 Match 多处使用同一个固定 `gameSpeed` 推导绝对开始时间和截止时间。若只更新速度字段而不改为可变速逻辑时钟，时间会跳变，进度校验及 Boss 加时也会失真。因此实施必须先统一时间源，再连接 SDK 回调和消息广播；不能把客户端 `runner.js` 的本地时钟作为权威实现。
